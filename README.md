# 应物音形足下输入法

> **《应物音形足下输入方案》**
> 版本 0.1.0　｜　千里之行，始于足下

一套以**全拼承担读音、部件承担字形**的汉字输入方案。

```text
全拼  →  加一个部件码  →  加第二个部件码
```

部件码取该部件**名称**的拼音首字母。名称，不是读音 —— 这是整套方案的支点。

---

## 一、为什么要有这个方案

它从[应物输入法](../hengma-native)（衡码）分出来，针对的是衡码的一处真实痛点。

衡码用「结构码＋部首码」消歧。测下来，**结构码的信息效率只有 57.7%** —— 三分之二的汉字都是左右结构，`z` 一个键覆盖 66.4%，几乎排除不掉什么。而部首码虽然有力，却要求使用者**知道哪个部件是部首、且知道它的通称**：`氵` 要知道叫「水」，`礻` 要知道叫「示」并且不能和 `衤`（衣）搞混。

足下换了个思路：**不问哪个是部首，你认得哪个部件就用哪个。**

实测结果（按字频加权）：

| 方案 | 打满时首选命中 | 平均码长 |
|---|---:|---:|
| 衡码　全拼＋结构＋部首 | 94.21% | 4.95 键 |
| **足下　全拼＋两个部件** | **94.67%** | **4.99 键** |

**同样的击键数、同样的准确率，但不需要认识部首。** 这就是足下买到的东西 —— 它不更快，它更容易。

## 二、编码规则

### 2.1 音：全拼

不带声调的标准汉语拼音，`ü` 写作 `v`。多音字按读音分别成码。

按字频加权平均 2.95 键，是编码成本的主体。

### 2.2 形：部件码

取部件**名称**的拼音首字母：

```text
清 = 氵 + 青      氵 叫「水」shuǐ → s      青 qīng → q      →  qingsq
请 = 讠 + 青      讠 叫「言」yán  → y                        →  qingyq
情 = 忄 + 青      忄 叫「心」xīn  → x                        →  qingxq
晴 = 日 + 青      日        rì   → r                        →  qingrq
字 = 宀 + 子      宀 叫「宝盖」bǎo → b     子 zǐ → z         →  zibz
```

因此**变体写法与本字同码**：`氵`＝`水`＝s，`讠`＝`言`＝y，`扌`＝`手`＝s。写法变了，名字没变，码就没变。

### 2.3 三条放宽规则

方案刻意把「能打出来的码」放宽，因为**一个没人猜得到的码等于不存在**。

**其一，任意两个部件皆可。** 三部件以上的字不强制用哪两个：

```text
轻 = 车 + 又 + 工
     车 chē → c    又 yòu → y    工 gōng → g
     可打  cy  cg  yc  yg  gc  gy   六种皆可
```

**其二，顺序不限。** `qingsq` 与 `qingqs` 都是「清」。

**其三，一个部件可以有多个名称。** 这不是含糊，是承认现实：

```text
彳  有人叫「双人旁」(s)，有人读本音 chì (c)     两个码都认
冂  有人叫「同字框」(t)，有人读 jiōng   (j)     两个码都认
```

### 2.4 逐级加码

每一级都是有效编码，打到候选出现即可停：

| 级 | 码长 | 首选命中 | 平均候选 |
|---|---:|---:|---:|
| 全拼 | 2.95 | 56.2% | 39.0 |
| ＋一个部件 | 3.97 | 77.7% | — |
| ＋两个部件 | 4.99 | **94.7%** | 1.8 |

上表的命中率按「使用者随便挑一个认得的部件」计算。若总能挑到最优组合，两部件可达 97.1%；真实情况介于两者之间 —— 人挑的部件通常是显眼的那个，比随机要好。

### 2.5 不设结构码

衡码的 `z/s/b/d/p` 结构码在足下**被去掉了**，这是实测后的决定：

- 全拼＋两部件：4.99 键，94.67%
- 全拼＋结构＋两部件：5.99 键，96.80%

多按一键只换来 2.13 个百分点，不划算 —— 和当初判断衡码结构码「信息效率低」是同一个道理。

结构码也**不能做成可选的**：若 `qingz` 既可能是「左右结构」又可能是部件「竹/足/走」，编码就有歧义。要么全有，要么全无。

生成器保留了 `--structure` 开关，可随时切回含结构码的版本重新评估。

## 三、部件命名表

这是整个方案的地基，也是工作量所在。

8,215 个汉字拆出 **1,586 种一级部件**。其中：

| 状态 | 数量 | 说明 |
|---|---:|---|
| 已人工确定 | 约 120 种 | 高频部首、读音与通称分歧者、无读音的变体 |
| 按自身读音取码 | 约 1,460 种 | 本身就是常用字（青、工、又、田……），读音即通称 |
| 仍无可用名称 | 0 种 | 已全部补齐 |

表在 `data-tools/sources/component-names.yaml`，只登记**需要人工判断**的部件；其余由生成器按自身读音自动取码。改动该表后重新生成即可。

### 命名规模与覆盖的关系

一个字只要有**一个**部件没有合用的名称，这个字就打不全。因此覆盖率对命名量非常敏感：

| 命名部件数 | 完整可编码的字 |
|---:|---:|
| 100 | 10.9% |
| 300 | 43.5% |
| 800 | 84.1% |
| 1,586 | 99.2% |

目前 **97.4% 的字有两个或更多可用部件**，余下 250 字只有一个部件、60 字无部件（独体字与无分解数据者），这些字的编码止于较短的级别。

## 五、生成与测量

```bash
# 重建部件命名表脚手架（列出所有部件及其状态，供人工审阅）
python data-tools/build_component_sheet.py

# 生成单字词典

    --report build-reports/zuxia_generator_report.json
```
