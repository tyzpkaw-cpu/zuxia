# 应物音形足下输入法

> **《应物音形足下输入方案》**
> 版本 0.2.0　｜　千里之行，始于足下

一套以**全拼承担读音、部件承担字形**的汉字输入方案。

```text
全拼  →  加结构码  →  加一个部件码  →  加第二个部件码
```

部件码取该部件**名称**的拼音首字母。名称，不是读音 —— 这是整套方案的支点。

---

## 一、为什么要有这个方案

它从[应物输入法](../hengma-native)（衡码）分出来，针对的是衡码的一处真实痛点。

衡码用「结构码＋部首码」消歧。痛点不在结构码 —— 结构是**看一眼就知道**的，左右还是上下，不需要学。痛点在部首码：它要求使用者**知道哪个部件才是部首、并且知道那个部首的通称**。`氵` 要知道叫「水」，`礻` 要知道叫「示」并且不能和 `衤`（衣）搞混。认错部首，就打不出字。

足下只换掉后半段：**结构码照收，但不问哪个是部首 —— 你认得哪个部件就用哪个，两个即可，顺序不限。**

实测结果（按字频加权，与应物同一口径，见 §2.6）：

| 方案 | 满码键长 | 打满时首选命中 | 仍需选字 | 平均附加键 | 总击键／字 |
|---|---:|---:|---:|---:|---:|
| 应物　全拼＋结构＋部首 † | 4.96 | 94.10% | 5.90% | 0.685 | 3.65 |
| 足下　无结构对照（0.1.0 的码位） | 5.02 | 97.04% | 2.96% | 0.603 | 3.57 |
| **足下 0.2.0　全拼＋结构＋任意两部件** | **5.99** | **98.12%** | **1.88%** | 0.790 | 3.76 |

† 应物一行取自上游 0.57-heng 公布的指标（首选 94.1%、需选字 5.9%、平均附加键 0.685）；满码键长与总击键由公布值推算。足下两行是本仓库 `data-tools/measure_zuxia.py` 的实测输出，与上游同口径（见 §2.6）。

这笔账要照实说：**0.2.0 比 0.1.0 每字多按约 0.18 键**（3.75 对 3.57），换来的是需要动手选字的比例从 2.96% 降到 1.73%、满码平均候选从 1.75 降到 1.43。多出来的那一键不是白花的，但它确实是花出去的。

选择保留结构码的理由有三条：

1. **它大体上不用学。** 合体字看一眼就知道左右还是上下，不需要像部首码那样"知道哪个是部首、且知道它的通称"。
   ——**但独体字是例外**：结构码是从拆字数据机械推出来的，而那份数据把独体字拆成笔画，于是 `山` 算成包围、`口` 算成上下。见 §2.2 的提醒与 §2.7 的核对办法。
2. **它把同音的字提前分开。** 「见」（另读 xiàn）与「先」同音，结构码 `b`／`s` 一键分家；「无」与「武」同为 wu，也是 `s`／`b` 分家。没有结构码时，它们要等到部件码才分得开。
3. **它与应物的码位对齐。** 足下的前两段（全拼、全拼＋结构）与应物同构：`qingzs`（清）、`qingzx`（情）、`yingbg`（应）在足下 0.2.0 里都是有效的中间码（已抽样实测）。
   ——**逐字是否完全一致，尚未核对**；`data-tools/sync_structure.py` 可以一条命令核对并对齐，见 §2.7。

> **0.1.0 曾经去掉过结构码，那个决定基于一次错误的测量。** 当时用「逐字加权」算命中率，而应物公布的 94.1% 是「逐（码，字）对加权」；两个口径混在一张表里比较，得出了"结构码只值 2 个百分点"的结论。口径对齐后重测，结论反了 —— 而且「＋结构」这一级测出 74.43%／13.4 个候选，与应物公布的 73.9%／14.4 几乎重合，说明口径这回对上了。详见 [`docs/待你定夺.md`](docs/待你定夺.md) §1。

## 二、编码规则

### 2.1 音：全拼

不带声调的标准汉语拼音，`ü` 写作 `v`。多音字按读音分别成码。

按字频加权平均 2.97 键，是编码成本的主体。单靠全拼，首选命中 56.79%，平均 38.1 个同码候选。

### 2.2 形（一）：结构码

一个字母，描述整字的拆分方式，与应物的定义一致：

| 码 | 结构 | 例 | 占比 |
|---|---|---|---:|
| `z` | 左右 | 清、请、轻 | 66.4% |
| `s` | 上下 | 字、先、无 | 22.6% |
| `b` | 包围、半包围 | 国、见、武 | 8.3% |
| `p` | 品字形、交叠，以及**兜底** | 森、品、众 | 2.1% |
| `d` | 独体 | 木、土、工、田、王 | 0.6% |

三个相同部件叠成的字（森＝三木、品＝三口、众＝三人）归 `p`。

应物公布的分布是 66.4 / 22.7 / 8.3 / 1.8 / 0.8 —— 两边几乎重合，差别只在 `p`／`d` 的边界。

> **`d` 比你想的窄，`p` 是个兜底桶。** 结构码是从 IDS 拆字数据机械推出来的，而
> IDS 对独体字给的是**笔画树**：山 会推成「包围」、口 推成「上下」、月 推成「包围」。
> 只有 45 个字被明确标成 `d`（来自一张手写名单），其余独体字散落在 `p`／`b`／`s` 里。
> 应物的分布说明它多半也是这么算的，但**这只是推断，没有逐字核对过**。
> 要核对，见 §2.7。

加上结构码后：3.96 键，首选命中 74.43%，平均候选 13.4。这一级与应物的同一级（73.9%／14.4）几乎重合，因为两者本来就是同一套码。

### 2.3 形（二）：部件码

取部件**名称**的拼音首字母：

```text
清 = 氵 + 青  左右      氵 叫「水」shuǐ → s     青 qīng → q    →  qing z sq
请 = 讠 + 青  左右      讠 叫「言」yán  → y                     →  qing z yq
情 = 忄 + 青  左右      忄 叫「心」xīn  → x                     →  qing z xq
晴 = 日 + 青  左右      日        rì   → r                     →  qing z rq
字 = 宀 + 子  上下      宀 叫「宝盖」bǎo → b    子 zǐ → z       →  zi   s bz
```

（示意用空格分段，实际码是连写的 `qingzsq`、`zisbz`。）

因此**变体写法与本字同码**：`氵`＝`水`＝s，`讠`＝`言`＝y，`扌`＝`手`＝s。写法变了，名字没变，码就没变。

### 2.4 三条放宽规则

方案刻意把「能打出来的码」放宽，因为**一个没人猜得到的码等于不存在**。

**其一，任意两个部件皆可。** 三部件以上的字不强制用哪两个：

```text
轻 = 车 + 又 + 工   左右 → qingz
     车 chē → c    又 yòu → y    工 gōng → g
     qingz 之后可打  cy  cg  yc  yg  gc  gy   六种皆可
```

**其二，顺序不限。** `qingzsq` 与 `qingzqs` 都是「清」。

**其三，一个部件可以有多个名称。** 这不是含糊，是承认现实：

```text
彳  有人叫「双人旁」(s)，有人读本音 chì (c)     两个码都认
冂  有人叫「同字框」(t)，有人读 jiōng   (j)     两个码都认
```

两个部件的首字母**允许相同**：`无`＝`一`(y)＋`尢`(y)，满码就是 `wusyy`。这不是 bug，是两个不同部件恰好同名首字母。

### 2.5 逐级加码

每一级都是有效编码，打到候选出现即可停：

| 级 | 平均键长 | 首选命中 | 前三命中 | 平均候选 |
|---|---:|---:|---:|---:|
| 全拼 | 2.97 | 56.79% | 80.65% | 38.1 |
| ＋结构 | 3.96 | 74.43% | 92.93% | 13.4 |
| ＋一个部件 | 4.99 | 90.86% | 98.74% | 4.0 |
| ＋两个部件 | 5.99 | **98.12%** | 99.96% | 1.5 |

上表按「逐（码，字）对、以字频为权」统计，即：使用者**随便挑一个认得的部件**，每种打法都按它实际会被用到的频次计入。若总能挑到最优组合，命中率还会更高；真实情况介于两者之间 —— 人挑的部件通常是显眼的那个，比随机要好。

### 2.6 关于口径

同一份词典，用两种加权方式算出来的"首选命中率"能差十个百分点，所以**口径必须写明**：

- **逐（码，字）对**（本文全部数字、应物公布数字均用此口径）：一个字有 N 种打法就计 N 次，每次按该字的字频加权。它回答的是"随手打出来的一个码，首选对不对"。
- **逐字**：一个字只计一次，问"这个字的所有满码里，有没有一个能首选命中"。它比前者乐观。

`data-tools/measure_zuxia.py` 两种都算，输出里分开标注。拿足下的数字和别的方案比之前，先确认对方用的是哪一种。

结构码是**强制的**，不能做成可选：若 `qingz` 既可能是「左右结构」又可能是部件「竹／足／走」，编码就有歧义。生成器保留了 `--no-structure` 开关，可以生成 0.1.0 那种无结构码的对照版本用于评估，但两种码**不能混用**。

### 2.7 与应物逐字对齐结构码

保留结构码的第三条理由（码位可迁移）只有在**两边给同一个字同一个结构码**时才成立。
足下自己推的结构码和应物的对不对得上，没有逐字验证过 —— 分布相近不等于逐字相同。

在装了应物的机器上跑一条命令即可核对，并把应物的判定抄过来：

```bash
python data-tools/sync_structure.py ../hengma-native/data/hengma.dict.yaml --dry-run   # 先看差异
python data-tools/sync_structure.py ../hengma-native/data/hengma.dict.yaml             # 再写入
python data-tools/generate_zuxia.py --report build-reports/zuxia_generator_report.json
```

它把结果写进 `data-tools/sources/structure-overrides.tsv`，生成器优先采信这张表。
文件为空就完全按生成器自己的判定走 —— **当前就是空的**。

## 三、部件命名表

这是整个方案的地基，也是工作量所在。

8,757 个汉字拆出 **1,586 种一级部件**。其中：

| 状态 | 数量 | 说明 |
|---|---:|---|
| 已人工确定 | 约 120 种 | 高频部首、读音与通称分歧者、无读音的变体 |
| 另加部件别名 | 210 条 | 「这个部件里看得见什么」，见下 |
| 按自身读音取码 | 约 1,460 种 | 本身就是常用字（青、工、又、田……），读音即通称 |
| 仍无可用名称 | 0 种 | 已全部补齐 |

表在 `data-tools/sources/component-names.yaml`，只登记**需要人工判断**的部件；其余由生成器按自身读音自动取码。改动该表后重新生成即可。

### 部件别名：「这个部件里看得见什么」

鹏 里看得见 月，打 `pengzy` 就该出鹏 —— 但 鹏 的一级部件是 朋 和 鸟，月 在第二层。
解决办法**不是**把 IDS 再递归一层：那样会拿到 艹＝十、⺼＝冫、火＝八人、马＝②
这类没人看得见的东西，而它们恰恰覆盖面最广（艹 451 字、土 244 字、王 191 字），
要全体字替它们买单。实测全递归的代价：

| | 一级（不加别名） | 全递归 | **人工勾选 210 条** |
|---|---:|---:|---:|
| 单字打满首选 | 98.27% | 97.64% | **98.12%** |
| 词组打满两部件首选（纯拼） | 99.40% | 97.83% | — |
| 词组每字一部件首选（纯拼） | 97.24% | 96.86% | **97.06%** |
| 码表行数 | 53,310 | 124,455 | **66,505** |

所以改成一条一条过目。收录标准三条，缺一不收：

1. 子部件在母部件里**看得见**，不是笔画树凑出来的；
2. 子部件有**通行叫法**，字母猜得到（䒑 没有读音也没有通名，不收）；
3. 新字母与母部件原有字母**不同**（鱼 里的「一」= y，与 鱼 本身同码，不收）。

效果：鹏 = `pengzy`（月），彭 = `pengzs`（士）／`pengzk`（口），崩 = `bengsy`。

> 前 8 条由 TYZPKAW 逐条勾选；其余 202 条按上述三条从 1,256 个候选里筛出，
> **未经人工逐条复核**。名单是开的，随时可加可删，改完重跑生成器与测量即可。

### 命名规模与覆盖的关系

一个字只要有**一个**部件没有合用的名称，这个字就打不全。因此覆盖率对命名量非常敏感：

| 命名部件数 | 完整可编码的字 |
|---:|---:|
| 100 | 10.9% |
| 300 | 43.5% |
| 800 | 84.1% |
| 1,586 | 99.2% |

目前 **96.9% 的字有两个或更多可用部件**（8,482 字），余下 241 字只有一个部件、34 字无部件（独体字与无分解数据者），这些字的编码止于较短的级别 —— 无部件的字满码就是「全拼＋结构」，4 键左右。

python data-tools/audit_zuxia.py --regen    # 外加两次重建逐字节比对

## 六、构建与安装

文本服务与安装程序由应物输入法的 TSF 层移植而来，两者**可以同时安装**：

```text
应物输入法           %ProgramFiles%\Yingwu     Win+Space 里显示「应物输入法」
应物音形足下输入法   %ProgramFiles%\Zuxia      Win+Space 里显示「应物音形足下输入法」
```

安装包、CLSID、注册表键、用户目录、图标全部独立，互不干扰。
移植怎么做、改了哪些地方，见 [`docs/工程排查.md`](docs/工程排查.md)。

### 6.1 构建文本服务

需要 Visual Studio 2022（含 C++ 桌面开发）与 CMake。

```powershell
# 渲染图标（只在本仓库重新克隆后需要跑一次）
pwsh scripts/make-icon.ps1 -Char 足 -Out src/ZuxiaTSF.ico
pwsh scripts/make-icon.ps1 -Char 足 -Out installer/setup/app.ico

# x64 + x86 编译并暂存到 dist\Zuxia
pwsh scripts/build.ps1 -Arch all -Configuration Release
```

### 6.2 无界面验证引擎

不用装、不用界面，直接拿真实的词典跑一遍：

```powershell
pwsh tools/build-engine-test.ps1 -Arch x64
copy tools/engine-test.exe dist/Zuxia/x64/
cd dist/Zuxia/x64; .\engine-test.exe
```

它必须在 `x64\` 目录里运行——`RimeEngine` 是从自己的模块路径找 `rime.dll` 和 `..\data` 的，
和文本服务运行时的行为一致。22 项断言覆盖候选编码注释、结构码分级、多音字取音、中文标点与中英切换。

> 断言不再钉死具体码串。加一条部件别名（比如「青 里看得见月」）就会让 清 从两个满码
> 变成四个，钉死字面量的话每加一条别名都要改测试，而它其实什么都没测出来。现在断言
> 的是不随别名改变的性质：**注释里的每个码都必须以已经打出的那几键开头**——承诺的码
> 必须真的打得到。`AnnotateCode` 恰恰在这里出过 bug（`行` 在 `hang` 下会多出一个指向
> 不存在的码的 `…`），所以这条性质值得单独盯。

### 6.3 打安装包

```powershell
pwsh installer/setup/make-setup.ps1            # 顺便重新构建文本服务
   # 或 -SkipBuild，当 dist\Zuxia 已经暂存好
```

产物是 `dist\ZuxiaSetup-<版本>.exe`（单文件、32 位、要求管理员权限）与同名 `.sha256`。
安装后**需要注销重新登录**，或在「设置 → 语言 → 键盘」里手动添加，才会出现在 Win+Space 列表里。

### 6.4 开发期脚本安装

不改注册表、不写「应用和功能」条目，只做 regsvr32，适合反复调试：

```powershell
pwsh installer/Install-Zuxia.ps1      # 需要管理员
pwsh installer/Uninstall-Zuxia.ps1 -PurgeUserData
```
