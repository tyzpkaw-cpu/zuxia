## 0 本轮已实测的诊断（所有编码类任务的共同前提）

作者的两个判断都成立，而且根因比他说的更靠前。证据全部是在本仓库源数据上跑出来的。

### 0.1 部件码「没穷尽」有三个互相独立的原因

**(a) 只拆一层，不递归。** `data-tools/generate_zuxia.py` 的 `components_of()` 只取
该字 IDS 串里出现的字符，不往下递归。于是：

| 字 | 现在拿到的部件 | 拿不到的部件 |
| --- | --- | --- |
| 傅 | 亻、尃 | 甫、寸 |
| 朝 | 龺、月 | 十、日 |
| 梳 | 木、㐬 | 亠、厶、川 |
| 揽 | 扌、览 | 见 |

递归一层（停在「已有名称的部件」或独体字）之后可用部件会变多的字：
**3047 字（37.24% 字数 / 13.33% 字频）**。

**(b) 部件没有名称时，拿它自己的生僻读音当字母。** `letters_for()` 在名称表里查不到
部件，就退回 `[部件本身]`，取它自己的拼音首字母：龺→g（gàn）、㐬→l（liú）、
尃→f（fū）、帀→z（zā）、叟→s（sǒu）。普通人不可能猜到这些。

规模：顶层用到的部件共 **1586 种**，其中 **1261 种没有名称**。
**整个字一个可猜部件都没有** 的字：**2365 字（28.90% 字数 / 34.46% 字频）**。
`data-tools/sources/component-names.tsv` 里 1447 条还挂着 `proposed`、只有 75 条
`settled`，就是这笔账。

**(c) 独体字的部件码来自已被本项目判定为不可信的笔画树。** 生成器对独体字的*结构码*
走 GF 0013—2009（正好 256 字，强制校验），但*部件码*仍然读 IDS 的笔画分解：

- 雨：`hanzi-dictionary` 给 `⿻帀？` → 部件只剩 帀（zā）→ 全码 `yudz`
- 月：`⿵冂二` → 冂（同字框 j / 冂 t）+ 二（e）→ `yuedj yuedt yuede yuedje yuedte ...`

仍然被生成部件码的独体字：**233 字（2.85% 字数 / 18.79% 字频）**。

另外 `衍` 不属于这一类但同样是源数据问题：`hanzi-dictionary` 把它记作 `⿻行氵`
（氵 插进 行 里），所以部件是 行、氵，拿不到 彳；cjkvi-ids 给的是 `⿲彳氵亍`。
`INFIX_HOSTS` 只列了 行、雔、衣 三个宿主，街/衡/衝 这一族都走这条路。

### 0.2 「需要再补一次部件码」成立，但单独加第三个几乎没用

顶层可用部件个数分布：`{0:32, 1:223, 2:7572, 3:309, 4:37, 5:9, 6:1}`。
92.5% 的字顶层只有两个部件 —— 不递归的话，第三个部件根本不存在。

同一口径（按字频加权、看「码打满之后该字有没有一个只属于它的码」）下实测：

| 方案 | 单字码表行数 | 打满后没有唯一码的字 |
| --- | --- | --- |
| 现状（顶层 / 任意两个 / 顺序不限） | 66,505 | 2,535 字（30.98% / 字频 19.06%） |
| 现状 + 允许第三个部件 | 68,415 | 2,463 字（30.10% / 17.31%） |
| 递归 + 任意三个 + 顺序不限 | 181,008 | 1,400 字（17.11% / 15.54%） |
| **递归 + 固定书写顺序 + 最多四个** | **46,734 ~ 48,904** | **1,108 字（13.54% / 12.05%）** |

「现状 66,505 行」与仓库 `docs/应物音形汉字键入方案.md` 公布的数字一致，说明这套
模拟是忠实的。

要点：**只加第三个部件 ≈ 白做（少 72 字）；只递归不改顺序 → 码表翻 2.7 倍；
递归 + 固定顺序 → 码表反而小 26%，不唯一字少 56%。**
乱序之所以贵，是因为它按排列数展开（n 个部件取 k 个有 n!/(n−k)! 种），
一旦部件数从 2 涨到 4，排列数就爆了。

### 0.3 GF 0014—2009 能一次解决 (b)，而且不破坏任何现有编码

国家标准《现代常用字部件及部件名称规范》给出 441 组 514 个部件及其**官方名称**
（宝盖、草字头、病字框、倒八、敖字旁、私字边……）。这跟结构码用 GF 0013—2009
是同一个思路、同一个家族的标准。

已取得公开转录本并存入 `data-tools/sources/gf0014-components.txt`（480 个有 Unicode
码位的部件 + 30 个只能用 IDS 描述的）。实测把它并进名称表之后：

- **整字一个可猜部件都没有：2365 字（28.90% / 字频 34.46%）→ 72 字（0.88% / 4.72%）**
- **与现有人工名称冲突、会让已有字母改变的部件：0 个**（纯增量，旧码全部照旧有效）
- 对「打满唯一性」几乎没有影响（同口径对比下只少 4 个字）——
  它解决的是**可猜性**，不是重码。

### 0.4 推荐的落地方案

```
国标名称表  +  递归拆分（停在已命名部件）  +  固定书写顺序  +  最多四个部件
            ∪  保留现有全部「任意两部件、顺序不限」的旧码作为别名
```

实测：单字码表 **78,440 行**（比现在多 17%），打满后没有唯一码的字
**1,218 字（14.88% / 字频 12.33%）**（现在 2,535 字 / 30.98% / 19.06%）。
向后完全兼容 —— 作者已经记住的乱序两部件码一条都不会失效。

### 0.5 还需要作者拍板的三件事

1. **长码的顺序**：推荐「固定书写顺序」（左→右、上→下）。旧的乱序两部件码保留为别名，
   所以不破坏肌肉记忆。要不要接受这个口径上的分裂（短码可乱序、长码必须顺序）？
2. **候选窗宽度**：见任务 6。现在是「稳定不跳动」，作者期待的是「贴合内容」。二选一。
3. **组字打一半按回车**：现在把原始码串当文本落进文档（已有断言钉死这个行为）。
   A 保持 / B 清空不落字。这个问题从上一轮问到现在还没有答案，任务 4 要用到它。

## 任务 2 递归拆分 + 固定顺序长码（依赖任务 1 · 需要 0.5 第 1 条的答案）

**为什么**：见 0.1(a)、0.2、0.4。

**做法**
- `components_of()` 旁边加 `deep_components_of()`：对每个顶层部件递归，

- `codes_for()` 增加固定顺序阶梯：`stem`、`stem+L1`、`stem+L1L2`、`stem+L1L2L3`、
  `stem+L1L2L3L4`，每一位取该部件的任一名称首字母（多名称则多条码）。
- 保留现有「任意两部件、顺序不限」的全部旧码，取并集。
- `max_code_length` 现在是 96，够用，不用动。

**已知会拆过头的地方（要在名称表里收口，属于任务 3 的工作面）**
- 梳 → 木 + 亠 + 厶 + 川。㐬 被拆碎了，不如整体，但 㐬 本身没人会读。
- 揽 → 扌 + 见。览 的上半部分递归后没有字母，丢了。
- 雨、月 这类独体字递归之后还是垃圾（源数据本身是错的）。

**验收**

- 新增断言：任一旧码（现有 66,505 行里的每一条）在新表里仍然存在。

## 任务 4 词码跟进（依赖任务 2 · 需要 0.5 第 3 条的答案）

**现象（作者实测）**
- `揽月` 必须打完整编码，而且部件码会落进文档。
- `梳毫` 打 `SHUHAO ZS MM` 之后还有好几个候选，没法再补部件码。
- `伏雨` 根本打不出来。

**根因**
`data-tools/generate_phrases.py` 的词码是「列式」的：全拼串 + 结构串 + **每个字各取一个
部件码**，而且那个部件码只取 `first[ch]`，也就是**每个字的第一个部件**。所以：
- 揽月 = `lanyue` / `lanyuezd` / `lanyuezd` + 扌(s) × 冂(j|t) → `lanyuezdsj`、`lanyuezdst`。
  作者想打的 `览(l)月(y)` 这条路词表里没有。
- 词码只有一层部件，没法「再补一次」。
- 伏雨 不是词，`base.dict.yaml` 里没有；`enable_sentence` 的逐字拼接**只对全拼那一档
  有效**（`data/zuxia.schema.yaml` 的注释已经写明：结构串和部件串是按列排的，
  Rime 的分词器切不动）。
- 没匹配上的时候 `express_editor` 把原始码串当文本提交 —— 这就是「部件码落进文档」。

**做法**
- 词码的部件段跟着任务 2 一起改成「每字可逐级加、按固定顺序」。
  注意行数会乘起来涨（现在 421,131 行 / 12.2 MB，Rime 首次部署已经要等几秒），
  要先算规模再决定每字最多给几个部件。
- 带形码的逐字拼接（`伏雨` 这类词表外组合）只能靠 `src/Decoder.cpp` 那个列式解码器，
  不能靠 Rime。先确认解码器要不要承担多字拼接。
- 「落进文档」的行为取决于 0.5 第 3 条的答案。

## 任务 5 Caps Lock 不生效（独立 · C++ · 不依赖任何编码改动）

**现象（作者实测）**：点「大写英文」不会变英文；必须先切英文、再按 Caps Lock。

**根因（已定位）**
- `data/zuxia.schema.yaml` 里的 `ascii_composer.good_old_caps_lock: true` 和
  `switch_key.Caps_Lock: clear` 对足下**完全不生效** —— 文件里自己的注释就写了：
  中/西切换是在 TSF 层用 `TF_MOD_ON_KEYUP` 预留键做的（`src/KeyEventSink.cpp`），
  Shift 和 Caps Lock 根本不会作为按键交给 librime。
- `src/KeyEventSink.cpp` 的 `_IsKeyEaten()` 只看「是不是中文模式」和「是不是字母/数字」，
  没有看 Caps Lock 状态。
- `src/RimeEngine.cpp:662` 还会把取到的字符统一压成小写。

**做法**
在 `_IsKeyEaten()` 里加一条：中文模式下，若 `GetKeyState(VK_CAPITAL) & 1` 为真
**且当前没有正在组字**，就不吃这个字母键，让 Windows 直接送大写字母出去。
（这是微软拼音、搜狗的通行行为。）正在组字时不要改行为，否则组字中途按 Caps Lock
会把已有编码甩掉。

**验收**
CI 能编过。真机：记事本里中文模式下按 Caps Lock，直接出大写字母；
再按一次回到中文；组字中途按 Caps Lock 不丢编码。
`scripts/audit-payload.ps1` 的 `$markers` 里加一个新日志标记便于验收。

## 任务 6 候选窗宽度（独立 · C++ · 需要 0.5 第 2 条的答案）

**现象（作者实测）**：键入窗口宽度不会自动变化。

**定位（读代码得出，未在真机量过）**
`src/CandidateWindow.cpp` 的 `RecalculateSize()` 竖排分支确实在按内容算宽度：

```
width = max(min_width, 最长行文字宽 + Scale(padding*4 + 44))
width = min(width, max_width)
```

`src/Settings.h` 的默认值是 `min_width = 220`、`max_width = 720`、`padding = 8`、
`font_size = 16`。九个单字候选的最长行大约是「9  字  注释」，量出来远不到 220，
所以宽度**始终卡在下限 220**，看起来永远不变。这是下限设得宽，不是算错了。

**两个方向，二选一**
- A 贴合内容：把 `min_width` 默认降到 120 左右。代价是每次按键宽度都会跳，晃眼。
- B 保持稳定：留 220，在设置文件的注释里写明「这是下限，短候选不会更窄」，
  并在设置界面把这两个值做成能直接调的。

无论选哪个，都应该在 `src/Settings.cpp` 的注释里把这个行为写清楚 ——
作者是看了设置里有 `min_width`/`max_width` 才以为是 bug 的。

## 任务 7 拆字窗：可移动的独立窗口，米字格里做拆字分析（依赖任务 2、3）

**作者原话**：「瘦」的部件码非常不清楚，所以需要这个。

**为什么要排在编码之后**：这个窗口要显示的就是「这个字拆成哪些部件、每个部件叫什么、
对应哪个字母」。而现在这份数据本身是坏的（龺→g、帀→z）。先修编码，
**这个窗口正好是编码的验收工具** —— 做出来之后一眼就能看出哪个部件名不可猜。

**做法要点**
- 独立顶层窗口，可拖动，不抢焦点（参照 `src/CandidateWindow.cpp` 的
  `WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW` 做法，但要能拖，所以不能用 `WS_POPUP` 裸窗）。
- 数据来源：不要在 C++ 里重算拆分。让 `generate_zuxia.py` 顺手导出一份

## 任务 8 `dt:` 日期 / `hl:` 农历（独立 · 不依赖编码）

**作者要求**：`dt:` 打出不同格式的日期（带时间 / 不带时间）；`hl:` 打出农历信息。

**做法**
Rime 的 `lua_translator` 在本项目里不可用（没有带 lua 的 librime 构建，
`scripts/fetch-librime.ps1` 拉的是标准发行包）。所以这两个前缀应该在 TSF 层做：
在 `src/KeyHandler.cpp` 里截住以 `dt:` / `hl:` 开头的编码串，直接生成候选，
不往 librime 送。

- `dt:` 用 `GetLocalTime`，给出若干固定格式（2025-10-01 / 2025年10月1日 /
  2025-10-01 14:30 / 周三 …）。
- `hl:` 农历需要查表或算法。公历↔农历换算必须查表才准，范围要写明白
  （比如只支持 1900—2100），并且**在文档里标注数据来源**。别自己推。

**验收**：两个前缀都要进 `tools/linux-selftest`，这样不依赖 Windows 就能测格式。
