# 应物音形汉字键入方案

> 原名：应物音形衡码输入法
> 方案版本 0.2.0　｜　本文所有数字均取自仓库现值，重出命令见 §5.5

一套汉字键入方案：**全拼承担读音，结构与部件承担字形**，二者按固定次序拼接成一枚编码。

```text
全拼  →  加结构码  →  加一个部件码  →  加第二个部件码
qing  →  qingz     →  qingzs        →  qingzsq        （清）
```

每一级都是可用的编码，打到候选出现即可停手。

---

## 一、名义

### 1.1 应物

> 承明心意以相应万物，而为变化。

「应物」二字出于此意。对一套键入方案而言，它指的是：键入的过程应当顺着写的人心里的那个字走，而不是让人去迁就工具的规则。汉字是音、形、义的结合体；一套与它相应的键入方式，所要求的也应当是关于这个字本身的认识——它怎么读、它怎么构成——而不是另一套专为机器设定的符号。

### 1.2 衡码

方案原名「应物音形衡码输入法」。「衡」取权衡之义：音与形在一枚编码里各据其位，不以一方压倒另一方。全拼承担读音，结构与部件承担字形，二者按固定次序前后拼接，分明而不相掩。

衡码有独立的实现（「应物输入法」），是本方案的前身。它用「结构码 ＋ 部首码」消歧，与本方案的分歧只在后半段：部首码要求使用者先知道**哪个部件才是部首**、并且知道那个部首的通称——`礻` 要知道叫「示」且不能与 `衤`（衣）相混，认错部首就打不出字。本方案改为「任意两个部件、顺序不限、允许多名」（§4.4），结构码照收。两套实现可以并存安装。

### 1.3 足下

实现本方案的 Windows 软件名为「应物足下输入法」，取「千里之行，始于足下」之意。方案是方案，软件是软件：本文只讲方案；软件的安装与使用见仓库的 [README](../README.md)。

### 1.4 作者与状态

本方案与其实现均出自一人之手，目前仍是**草案**：编码规则已定案并有实测，部件命名表已覆盖全部部件但待人工复核，软件可安装可打字但自动化测试未覆盖全部层次。本文凡属未经验证的判断，均在正文中标明。

## 二、缘起

### 2.1 其一：键入的准确性，是对思绪的保护

写作时真正稀缺的不是时间，是思绪的连续。一个念头从成形到落在纸上，中间任何一次停顿都可能让它散掉。键入是这条链上最末、也最频繁的一环——一篇三千字的文章要按下近万次键。这一环上的每一次迟疑、每一次回头修改，都是对上游那个念头的打断。

因此，一套键入方案的首要指标不应是峰值速度，而是**一次把字打对的比例**。

**拼音输入法在这一点上有结构性的困难。** 汉语单字同音极为严重。按本方案的字表实测：只给全拼、不给任何字形信息时，首选命中率为 56.79%，同一串拼音平均对应 38.12 个候选字（口径见 §5.4）。也就是说近一半的字要靠看候选列表来定。

现代拼音输入法用语言模型把这个数字压下去——按词、按句、按使用历史去猜——但这引入了另一个问题：**候选的顺序由使用者看不见的模型决定**。同一串拼音今天出这个、明天出那个；打错了，使用者既不知道为什么错，也无法保证下一次不错。判断权被交给了不可见的统计。

**在当下的教育语境里，这个困难还被放大了一层。** 汉语拼音是识字的脚手架，人人会写，于是拼音输入法几乎不需要学。代价是：使用者关于汉字**字形**的那一半知识——这个字是左右还是上下、它由哪些部件组成——在键入时完全闲置。一个人可能认得三千字的写法，但在键盘上这三千字的形他一个也用不上。

**五笔输入法走的是另一端，它的困难在入口。** 五笔只认字形、不认读音，因此不受同音之困，熟练者的速度上限很高。但它要求使用者先学会一套**专为输入而设**的知识：字根如何分区、如何落在键位上、末笔交叉识别码如何补足。这套知识在输入法之外没有用处，学了只能用来打字；而它的记忆量足以让多数人在入门阶段就停下。此外，只认形也意味着一旦遇到不会拆的字，使用者没有第二条路——读音这条他本来就有的路被关掉了。

本方案试图不走这两端中的任何一端。

### 2.2 其二：键入的方式是否参与思维的进路

这是一个尚无定论的问题。本方案不假装有答案，只把它摆出来，并说明自己按哪一边下注。

拼音键入的过程大致是：

```text
意  →  音  →  拼音串  →  候选列表  →  视觉检索  →  确认
```

中间多出一步**视觉检索**：候选列表要读一遍、比一遍。这一步调用的是视觉与比对，与正在进行的写作并不同路；它每发生一次，就是一次短暂的切轨。

音形并取的键入过程是：

```text
意  →  字（音与形）  →  码
```

它要求的是对那个字本身的认识。当码足够长、候选足够少时，视觉检索这一步被压缩，甚至不再发生。

这个差别是可度量的。同一份字表，按使用频次加权：

| 打到哪一级 | 平均候选数 |
|---|---:|
| 只给全拼 | 38.12 |
| 加结构码 | 12.58 |
| 加一个部件 | 4.16 |
| 加两个部件 | 1.43 |

从 38 到 1.43，是二十余倍的检索量差别。

**但必须如实说明：这个差别不是零。** 实测中约三分之一的字（按使用频次约四分之一）无论怎么打都不唯一，仍要选一次字（§5.4）。「完全不看候选」做不到，本方案不作此承诺。

那么，**汉字如何键入才是更好的**？本方案的回答是：**让键入所依赖的知识，与汉字本身的构成相一致。** 汉字是音形义的结合体。只取音，是把它当作拼音的转写；只取形，是把它当作图形。音与形并取、次序分明，才与这个字本来的样子相对应——这也正是「应物」二字的意思。

### 2.3 其三：规则应当可被完整理解，而规则所需的知识应当是使用者已有的

输入法是日常工具里被调用得最频繁的一个，一天数千次。正因为频繁，它的行为是否**可预测**就不只是方便问题，而决定了使用者与工具之间的关系。

这里有两件事，应当分开要求。

**第一件：规则本身可被完整理解。**

本方案的编码是确定的：同一串码永远给出同一组候选，顺序只由字频决定，不受使用历史、不受上下文、不受任何不可见模型影响。由此得到一个具体的性质——**打错了，使用者能自己看出错在哪一位**。第 3 位是结构，第 4、5 位是部件；候选不对，是结构判错了，还是部件的名字记成了别的，一眼能定位，下一次自己能改对。在候选顺序由模型决定的方案里，「候选不对」是一件没有原因可查的事，使用者只能重试。

这条性质也划出了本方案的一条边界：**不做通用的模糊纠偏**。容错应当做在规则层（例如把方言里常见的音混同登记为等价输入），不做在算法层。算法一旦开始猜使用者想打什么，「能自己看出错在哪一位」就不再成立。

> 附带说明一处曾经的错误论据。这条取舍一度被表述为「纠偏会让『码打满就唯一』这条性质失效」。该表述的事实部分是错的：实测满码唯一率只有 82.45%（§5.4）。结论本身仍然成立，但它立足于可解释性，不立足于唯一性。

**第二件：规则所需的知识，应当是使用者已经拥有的。**

本方案只用三样东西：

| 要素 | 来源 |
|---|---|
| 读音 | 汉语拼音，识字教育的起点，人人已会 |
| 整字结构 | 左右、上下、包围、品字、独体，规范汉字教学的基本内容 |
| 部件名称 | 三点水、言字旁、宝盖头、提手旁，语文课上就是以「这个部件叫什么」的形式教的 |

这三样都不是为输入法新造的。本方案不要求使用者记住任何一张专用的字根表或键位图；它要求的，是把已经学过的东西用起来。

与 §2.1 的两端对照看最清楚：拼音输入法只用了其中第一样，另两样闲置；五笔三样都不用，而要求另学一套；本方案三样都用，且都是现成的。

**代价要说清。** 「现成」不等于「不用想」。结构大体上看一眼就知道，确实不用学；部件名称则参差——「三点水」人人会说，一个生僻部件叫什么，使用者未必有现成的叫法。本方案为此设了三条放宽规则（§4.4）：任意两个部件皆可、顺序不限、一个部件允许多个名称。这些放宽是承认现实，不是含糊。

## 三、设计思路与原则

### 3.1 音形并取，次序固定

一枚编码分三段，次序不可换：全拼在前，结构居中，部件在后。固定次序换来的是可读性——看到 `qingzsq`，使用者能把它切回「qing / z / s+q」，知道每一位在说什么。

### 3.2 逐级加码，打到够用为止

三段不必打满。`qing`、`qingz`、`qingzs`、`qingzsq` 都是有效编码，候选出现就可以停。常用字往往在第一、二级就已首选命中，生僻字才需要打到满码。**编码长度随需要而变，不是定长。**

### 3.3 放宽到「猜得到就能打」

一个没人猜得到的码等于不存在。因此：三部件以上的字不规定该用哪两个；部件的先后不论；一个部件允许有多个名称（通称与本音皆可）。宁可一个字多出几条编码，也不要使用者卡在「这个部件到底该叫什么」上。

这一条的代价是编码行数增加（§5.3），收益是不会把人挡在门外。

### 3.4 规则确定，不猜使用者的意图

同一串码永远给出同一组候选。排序只看字频，不看上下文、不看使用历史。使用者的选择会被记住（见 §3.7），但记住的方式也是确定的、可查的。

### 3.5 判定以国家标准为据，不以程序推断为据

独体字的判定以《GF 0013—2009 现代常用字部件及部件名称规范》的独体字表为准（`data-tools/sources/gf0013-duti.txt`）。此前版本从拆字数据机械推断，而拆字数据对独体字给出的是**笔画树**，于是「山」被推成包围、「口」被推成上下、「月」被推成包围——与任何人的直觉都不符。改为查表后，山、口、月、木、田、一、见 一律判为独体。程序推断只用于标准表以外的字。

### 3.6 一切指标可复现

本文、README 与仓库文档中的每一个数字，都能用仓库里的脚本重新算出来（§5.5）。数据改了，数字就该跟着改，不手抄。

### 3.7 使用者的数据留在本机

键入过程中产生的个性化数据（选过哪个候选）只写在本机的用户目录下，纯文本，使用者随时可以打开查看，删掉即等于忘掉全部。诊断日志只记事件，不记内容——使用者打了什么字、选了什么候选，一个字都不记。

## 四、编码规则

### 4.1 音：全拼

不带声调的标准汉语拼音，`ü` 写作 `v`。多音字按读音分别成码。

按字频加权平均 2.97 键，是编码成本的主体。单靠全拼，首选命中 56.79%，平均 38.12 个同码候选。

### 4.2 形（一）：结构码

一个字母，描述整字的拆分方式：

| 码 | 结构 | 例 | 字数占比 | 按字频加权 |
|---|---|---|---:|---:|
| `z` | 左右 | 清、请、轻 | 66.39% | 43.69% |
| `s` | 上下 | 字、先、花、安 | 21.83% | 20.86% |
| `b` | 包围、半包围 | 国、武、回、风 | 7.85% | 11.86% |
| `p` | 品字形、交叠，以及兜底 | 森、品、众 | 0.65% | 0.34% |
| `d` | 独体 | 木、田、山、口、月、一、见 | 3.28% | 23.24% |

两列是两种口径：「字数占比」的分母是 8,757 个（字，读音）对，未加权；「按字频加权」是同一批对按字频加权。二者相差最大的是 `d`——独体只占三个百分点的字数，却占近四分之一的**使用**频次，因为最常用的一批字（一、人、口、山、日、月）大半是独体。评估「好不好学」看左列，评估「打起来什么感觉」看右列。

加上结构码后：3.96 键，首选命中 74.75%，平均候选 12.58。

### 4.3 形（二）：部件码

取部件**名称**的拼音首字母——名称，不是读音。这是整套方案的支点。

```text
清 = 氵 + 青   左右     氵 叫「水」shuǐ → s     青 qīng → q     →  qing z sq
请 = 讠 + 青   左右     讠 叫「言」yán  → y                     →  qing z yq
情 = 忄 + 青   左右     忄 叫「心」xīn  → x                     →  qing z xq
晴 = 日 + 青   左右     日        rì   → r                     →  qing z rq
字 = 宀 + 子   上下     宀 叫「宝盖」bǎo → b    子 zǐ → z       →  zi   s bz
```

（示意用空格分段，实际编码连写：`qingzsq`、`zisbz`。）

取名称而非读音，带来一条有用的性质：**变体写法与本字同码**。`氵`＝`水`＝s，`讠`＝`言`＝y，`扌`＝`手`＝s。写法变了，名字没变，码就没变。

### 4.4 三条放宽规则

**其一，任意两个部件皆可。** 三部件以上的字不规定用哪两个：

```text
轻 = 车 + 又 + 工    左右 → qingz
     车 chē → c     又 yòu → y     工 gōng → g
     qingz 之后  cy  cg  yc  yg  gc  gy  六种皆可
```

**其二，顺序不限。** `qingzsq` 与 `qingzqs` 都是「清」。

**其三，一个部件可以有多个名称。**

```text
彳   有人叫「双人旁」(s)，有人读本音 chì (c)     两个码都认
冂   有人叫「同字框」(t)，有人读 jiōng   (j)     两个码都认
```

两个部件的首字母允许相同：`无`＝`一`(y)＋`尢`(y)，满码是 `wudyy`。这不是缺陷，是两个不同部件恰好同名首字母。

**其四（放宽规则的延伸），部件别名：「这个部件里看得见什么」。**

「鹏」里看得见「月」，使用者打 `pengzy` 就应该出「鹏」——但鹏的一级部件是「朋」与「鸟」，月在第二层。

解决办法**不是**把拆分再递归一层。全递归会拿到 艹＝十、⺼＝冫、火＝八人、马＝② 这类没人看得见的东西，而它们恰恰覆盖面最广（艹 451 字、土 244 字、王 191 字），要让全体字替它们买单。实测对照：

| | 只取一级 | 全递归 | **人工勾选 210 条** |
|---|---:|---:|---:|
| 单字打满首选 | 98.27% | 97.64% | **98.16%** |
| 编码行数 | 53,310 | 124,455 | **66,505** |

所以改为一条一条过目。收录标准三条，缺一不收：

1. 子部件在母部件里**看得见**，不是笔画树凑出来的；
2. 子部件有**通行叫法**，字母猜得到（「䒑」既无读音也无通名，不收）；
3. 新字母与母部件原有字母**不同**（「鱼」里的「一」＝y，与「鱼」本身同码，不收）。

效果：「鹏」可以用看得见的「月」(y) 来打——`pengzy` 的候选里有鹏，满码 `pengzyn`（月＋鸟）唯一；「崩」同理，`bengsy` 首选命中。

别名只是**多给一条路**，不保证首选：`pengzy` 的首选是字频更高的「朋」。首选顺序一律由字频决定，别名不参与排序。

现收 210 条。其中前 8 条逐条勾选，其余 202 条按上述三条从 1,256 个候选里筛出，**未经人工逐条复核**。名单是开放的，可加可删。

### 4.5 逐级加码

| 级 | 平均键长 | 首选命中 | 前三命中 | 平均候选 |
|---|---:|---:|---:|---:|
| 全拼 | 2.97 | 56.79% | 80.65% | 38.12 |
| ＋结构 | 3.96 | 74.75% | 93.18% | 12.58 |
| ＋一个部件 | 4.99 | 89.78% | 98.62% | 4.16 |
| ＋两个部件 | 5.99 | **98.16%** | 99.96% | 1.43 |

合计：平均附加键 0.787，总击键 3.76 键／字，打满后仍需动手选字的比例 1.84%。

上表按「逐（码，字）对、以字频为权」统计：使用者随便挑一个认得的部件，每种打法都按它实际会被用到的频次计入。若总能挑到最优组合，命中率还会更高；真实情况介于两者之间——人挑的部件通常是显眼的那一个，比随机要好。

### 4.6 词

词的编码与单字同构，只是按**列**排：全拼串 ＋ 逐位结构串 ＋ 逐位部件串。

```text
苏瑶      su yao        +  s z    +  c(艹) w(王)          →  suyao / suyaosz / suyaoszcw
你好      ni hao        +  z z    +  r(人) n(女)          →  nihao / nihaozz / nihaozzrn
杨志鹏    yang zhi peng +  z s z  +  m(木) s(士) p(朋)
部首      bu shou       +  z d                            →  bushou / bushouzd
```

三档都是有效编码，打到候选出现就停——与单字的逐级加码是同一套规则。单字是词的退化情形（n＝1），所以使用者只需记一套规则。

**词表这条路的部件位只认每个字的第一个部件**（左边的／上面的／外面的那一个），它的任何叫法都认。单字那边的「任意部件、任意顺序」查表做不到：全展开是 568 万行、150 MB，词典编译不动。

词表没有收的词（人名、生僻搭配）由**列式解码器**兜底：它不查词表，按「列」直接配，因此也不受上述限制。上例中的「部首」就不在词表里，`bushouzd` 仍然首选命中。解码器的规则见 [docs/列式解码.md](列式解码.md)。

词表收的是雾凇拼音（rime-ice）按词频取的前 12 万词。

### 4.7 关于口径

同一份词典，两种加权方式算出的「首选命中率」能差十个百分点，所以口径必须写明：

- **逐（码，字）对**（本文全部数字均用此口径）：一个字有 N 种打法就计 N 次，每次按该字的字频加权。它回答的是「随手打出来的一个码，首选对不对」。
- **逐字**：一个字只计一次，问「这个字的所有满码里，有没有一个能首选命中」。它比前者乐观。

拿本方案的数字与别的方案比较之前，请先确认对方用的是哪一种。

### 4.8 结构码是强制的

结构码不能做成可选项。若 `qingz` 既可能表示「左右结构」，又可能表示部件「竹／足／走」，编码就有歧义。生成器留有 `--no-structure` 开关，可生成无结构码的版本用于评估，但两种编码**不可混用**。

### 5.2 部件命名表

8,757 个汉字拆出 **1,586 种一级部件**。

| 状态 | 数量 | 说明 |
|---|---:|---|
| 已人工确定 | 约 120 种 | 高频部首、读音与通称分歧者、无读音的变体 |
| 部件别名 | 210 条 | 「这个部件里看得见什么」 |
| 按自身读音取码 | 约 1,460 种 | 本身就是常用字（青、工、又、田……），读音即通称 |
| 仍无可用名称 | 0 种 | 已全部补齐 |

表只登记**需要人工判断**的部件，其余由生成器按自身读音自动取码。这张表是整个方案的地基，也是工作量所在，目前**已覆盖全部部件但待人工复核**。

### 5.3 有无结构码的对照

本方案的 0.1.0 曾去掉结构码，0.2.0 加了回来。两版同口径实测：

| 版本 | 满码键长 | 打满时首选命中 | 仍需选字 | 平均附加键 | 总击键／字 | 满码平均候选 |
|---|---:|---:|---:|---:|---:|---:|
| 0.1.0　全拼＋任意两部件 | 4.99 | 96.52% | 3.48% | 0.626 | 3.60 | 1.87 |
| **0.2.0　全拼＋结构＋任意两部件** | 5.99 | **98.16%** | **1.84%** | 0.787 | 3.76 | **1.43** |

这笔账照实说：**0.2.0 比 0.1.0 每字多按约 0.16 键**，换来的是需要动手选字的比例从 3.48% 降到 1.84%、满码平均候选从 1.87 降到 1.43。多出来的那一键不是白花的，但它确实是花出去的。

保留结构码的三条理由：

1. **它大体上不用学。** 合体字看一眼就知道左右还是上下，不需要像部首码那样先知道「哪个是部首、且它的通称是什么」。
2. **它把同音字提前分开。** 「见」与「先」同音，`d`／`s` 一键分家；「无」与「武」同为 wu，也是 `d`／`b` 分家。没有结构码时，它们要等到部件码才分得开。
3. **它与衡码的码位同构**，便于在两套实现之间迁移。

### 5.4 已知的不足

**「码打满就唯一」是不对的。** 实测：

| 口径 | 数值 |
|---|---:|
| 打满时唯一的码占比（按码数） | 82.45% |
| 打满仍不唯一的字 | 2,669 个（字数 32.62%，字频 23.45%） |
| 任何长度都不唯一的字 | 2,631 个（字数 32.15%，字频 22.96%） |

约三分之一的字、近四分之一的使用频次，**无论怎么打都得选一次字**。例如 `yid` 同时是 一／已／衣／义／亦／夷／乙，`qingzs` 是 清／碃。

满码首选命中 98.16% 与这件事并不矛盾——不唯一不等于不排第一，字频高的那个通常排第一。但「唯一」这个词不能再用来为设计取舍背书。

其余已知欠账：

- **部件命名表待人工复核。** 约 1,460 种部件的取码由程序按自身读音自动给出，未经逐条审阅。
- **无反查。** 想不起某个字的结构位或部件名时，目前没有出路。
- **部件别名不全。** 「出」在一般人眼里是两个「山」，而现行编码只认 `c`（屮）与 `q`（凵）。
- **与衡码的结构码判定有 207 字分歧**，占输入频率 13.69%。本方案已改按 GF 0013—2009 判定，衡码那边尚未跟进；两边是否逐字一致，**未经核对**。在同时装有两套数据的机器上，`data-tools/sync_structure.py` 可一条命令核对并对齐。
