### 第一轮抓到的实质缺陷：52 行假候选，0.1.0 起就在发

不变量 1、2 第一次跑就红了：

```
# 屄	bi	1
# 那	nei	9929703
# 唔	ng  没启用	1
# 丼	jing / dan	1
```

字表源 `8105.dict.yaml` 在正文区里用 `#` 注掉了 33 行（脏话、异体、未启用读音），
另有几行把说明文字写在读音列。`load_charset` 从来没有跳过注释行，于是：

- **`# 那` 成了 `nei` 的候选，权重 9,929,703** —— 会排在候选窗很靠前的位置，
  显示出来就是一个带井号的「# 那」；
- `ng  没启用`、`jing / dan` 变成了带空格和汉字的"码"，越出 Rime 的字母表。

这是**存量缺陷**，0.1.0 的 44,579 行里同样有，只是当时没人查。

**已修**：`load_charset` 跳过 `#` 开头的行，并要求读音是纯 ASCII 字母，
否则计数丢弃。修后字表 8,783 → 8,757 字，行数 53,362 → 53,310。

## 第二轮：对抗式复审

### 2.1 〔最高〕结构码对不对得上应物，没有逐字验证过

保留结构码的三条理由里，第三条是「与应物码位对齐、肌肉记忆可迁移」。
这条只有在**两边给同一个字同一个结构码**时才成立，而目前：

- 足下的结构码是从 IDS 拆字数据机械推出来的；
- IDS 对独体字给的是**笔画树**，推出来的结构码近乎随机 ——
  `山` → `b`（包围）、`口` → `s`（上下）、`月` → `b`、`火` → `p`、`又` → `p`；
- 明确标成 `d` 的只有 **45 字**，全部来自生成器里一张手写名单。

抽查 35 个常见独体字：16 个在全拼级就已经是首选（结构码用不上），
**19 个需要继续打**，而那 19 个的结构码没有一个是使用者猜得到的。

**这不等于"错"。** 应物公布的分布是 z 66.4／s 22.7／b 8.3／p 1.8／d 0.8，
足下是 66.4／22.6／8.3／2.1／0.6 —— 几乎重合，说明应物多半也是这么推的，
而作者天天在用应物。但**分布相近不等于逐字相同**，而这是唯一一处"不同就静默
失效"的地方：结构码差一个字母，共用的那一级就没了，人不会收到任何提示。

**处置**：加了一条可核对、可覆盖的通路，不猜。

- 生成器新增 `--structure-map`，读 `data-tools/sources/structure-overrides.tsv`，
  该表优先于自身判定；**当前文件为空**，行为与改动前完全一致（已验证：
  空表与无表生成的词典逐字节相同）。
- 新增 `data-tools/sync_structure.py`：在装了应物的机器上一条命令把应物词典里
  每个字的结构码抄进那张表，并先用 `--dry-run` 打印逐字差异。
- 自测：用足下自己的词典当输入跑一遍，取到 8,183 字、0 字取不准、0 字差异；
  往返（导出→重新生成）逐字节一致；人为把 `山` 改成 `d` 后，`shand…` 确实出现。

**待你执行**（这台机器上没有应物仓库）：

```bash
python data-tools/sync_structure.py ../hengma-native/data/hengma.dict.yaml --dry-run
```

### 2.3 `kMaxCodes` 从 4 降到 3，且它在两个地方

满码从 5 键变 6–7 键，候选行里并排 4 个完整码放不下（`行` 的
`hangzcc hangzcs hangzsc` 已经 23 个字符）。降到 3。

陷阱是**这个常量在两处出现**：`src/RimeEngine.cpp`，以及
`tools/port_from_yingwu.py` 里那段会覆写它的 `ANNOTATE_NEW` 替换串。
只改前者，下次重跑移植脚本就会被打回 4，而且不会有任何报错。

**已改两处，并写成不变量 16／17**，`audit_zuxia.py` 每次都会比对。

### 2.7 无部件字与单部件字的满码很短

34 字无可用部件（满码＝全拼＋结构，约 4 键），241 字只有一个部件（约 5 键）。
这不是 bug：`maximal_codes` 对它们产出短码是正确行为，注释表也照收
（不变量 12 覆盖）。代价是这些字打满了仍可能不唯一 —— 属于部件命名表的覆盖
问题，不是码位设计问题。

全表口径：**打满仍不唯一的字占 24.3% 字频**，但按（码，字）对加权的
"打满后仍需选字"只有 **1.73%** —— 两个数不矛盾：不唯一的那些字大多排第一。

### 2.8 三叠式规则是照应物 README 的文字实现的

`森`＝三木、`品`＝三口、`众`＝三人 归 `p` 而不是 `s`。
这条是移植时漏掉、这次补回的，依据是**应物 README 的文字描述**，
**没有看过应物的生成器源码**。若 2.1 的逐字核对做了，这条会被一并覆盖。

### 2.9 README 的数字，全部重出

旧 README 的三级表（56.2 / 77.7 / 94.7）三行口径不一致，而且 94.67% 是用
**逐字加权**算的、却拿去和应物**逐（码，字）对**的 94.1% 比。
现在全表统一为逐（码，字）对、按字频加权，并在 §2.6 写明口径差异。

`measure_zuxia.py` 也改了：能还原每个码属于哪一梯（靠读音数据，不能只看码长
—— `行` 的 `hangz` 和 `xingz` 长度不同却是同一梯），输出分段表、平均附加键、
打满后需选字，与应物的 0.685 同口径。

## 第三轮：CI 上真跑（2026-09-27 晚）

GitHub Actions：`码表不变量`（ubuntu）＋`编译与打包`（windows）。

**第一轮的 21 项不变量在干净检出上全绿**，两次重建逐字节一致。

**Windows 侧编译通过，20 项断言红了 1 条 —— 而且红得对。**

```
行 under `hang` shows only its hang codes           FAIL
实际输出：行[hangzcc hangzcs hangzsc …]
```

多出来的 `…` 是 `AnnotateCode` 的一个**真 bug**，不是期望值写错：循环先判上限、
后判前缀，3 个匹配码显示完之后，迭代器还要走到 `heng*`／`xing*` 那些被前缀排除的
条目，一撞 `shown == kMaxCodes` 就补了个省略号。**它在承诺一些并不存在的码。**

0.1.0 时上限是 4、`行` 每个读音只有 3 个满码，永远撞不到，所以这个 bug 一直躺着。
把上限降到 3 才让它浮出来 —— 这条如果不上 CI 真跑，纸面审计是看不见的。

**已修**：两个判断交换顺序，先过滤前缀再判上限。`src/RimeEngine.cpp` 与
`tools/port_from_yingwu.py` 的 `ANNOTATE_NEW` 同步改（不变量 16／17 守着）。

顺带确认的几件事，都来自 CI 的真实输出：

- `qingz`（只打到结构码）已经把候选收窄到 请／轻／清／情／晴，结构码这一级是有效的；
- `zisbz` → 唯一候选「字」；`qingzsq` → 清／碃 两个；
- 多音字按读音分流正确：`hang` 只出 `hangz*`，`xing` 只出 `xingz*`；
- 中文标点 7 项、中西文切换 6 项全过，移植层没被码位改动波及。
