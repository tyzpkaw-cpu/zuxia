## 一、我替你做了一个方案级决定：去掉结构码

**这是最需要你复核的一条。**

你原来的设想里保留了衡码的结构码（`z/s/b/d/p`）。我实测后去掉了，理由：

| 方案 | 打满时首选命中 | 平均码长 |
|---|---:|---:|
| 全拼＋两个部件 | 94.67% | 4.99 键 |
| 全拼＋结构＋两个部件 | 96.80% | 5.99 键 |

多按一键只换 2.13 个百分点。这和你我先前判断「衡码结构码信息效率只有
57.7%、不划算」是同一个道理，所以我按同一标准处理了。

另有一条硬约束：**结构码不能做成可选的**。若 `qingz` 既可能是「左右结构」
又可能是部件「竹/足/走」，编码就有歧义。只能全有或全无。

不同意的话一条命令切回：

```bash
python data-tools/generate_zuxia.py --structure --version 0.1.0
```

## 二、部件命名表需要人工复核

这是方案的地基，也是我最没把握的部分。

1,586 种部件里：

- **约 120 种我人工定了**（`data-tools/sources/component-names.yaml`）
- **约 1,460 种按自身读音自动取码** —— 这批是隐患所在

自动取码的前提是「读音即通称」。对「青、工、又、田」这类本身就是常用字的
部件成立，但**一定还有漏网的分歧**，就像我已经抓到的这几个：

```
彳  读 chì，通称「双人旁」      → 已收 s 和 c 两个码
丷  数据给 h，通称「八字头」    → 已改为 b
冂  读 jiōng，通称「同字框」    → 已收 t 和 j
```

**建议做法**：跑一遍脚手架，它会按覆盖字数排序列出全部部件：

```bash
python data-tools/build_component_sheet.py
# 输出 data-tools/sources/component-names.tsv
```

从覆盖字数最多的往下看，凡是「读音和你平时的叫法不一样」的，就往
`component-names.yaml` 里加一条。**一个部件可以有多个名称，不必二选一**——
多收一个码的代价远小于漏收。

前 100 个部件覆盖 50% 的字次，前 300 个覆盖 73%，从上往下看性价比最高。

## 五、一个我想请你确认的判断

足下**不比衡码快**。实测两者在相同击键数下准确率几乎相同（94.67% vs
94.21%）。它买到的是**不需要认识部首**——看见哪个部件眼熟就用哪个。

如果你期待的是「更快」，那方案方向要重新想；如果你要的是「更容易上手」，
那现在这个结果是达标的。

我按后者理解在推进，README 里也是这么写的。**这个理解对不对，请你确认。**
