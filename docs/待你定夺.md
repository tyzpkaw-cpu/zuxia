## 一、〔已结案〕结构码：去掉 → 加回来

**结论：加回来。0.1.0 去掉结构码的决定作废，0.2.0 采用「全拼＋结构＋任意两部件」。**

### 1.1 当初为什么去掉（以及错在哪）

当初摆出的是这张表：

| 方案 | 打满时首选命中 | 平均码长 |
|---|---:|---:|
| 全拼＋两个部件 | 94.67% | 4.99 键 |
| 全拼＋结构＋两个部件 | 96.80% | 5.99 键 |

"多按一键只换 2.13 个百分点，不划算" —— 这个判断有两处硬错：

1. **口径混用。** 94.67% 是用**逐字加权**算的（一个字只算一次，问"它的满码里
   有没有一个能首选命中"）；而拿来对标的应物 94.1% 是**逐（码，字）对加权**
   （一个字有 N 种打法就计 N 次）。两个数不可比。对齐到应物的口径后，能逐位
   复现应物脚本的输出，足下 0.1.0 的真实数字是 **97.04%**，应物是 **94.10%**。
2. **只看了命中率，没看选字成本。** 决策该看的是"打满以后还要不要动手选字"
   和"总击键／字"，不是单一的首选率。

### 1.2 对齐口径后的实测

| 方案 | 满码键长 | 打满首选 | 仍需选字 | 平均附加键 | 总击键／字 | 满码候选 |
|---|---:|---:|---:|---:|---:|---:|
| 应物　全拼＋结构＋部首 † | 4.96 | 94.10% | 5.90% | 0.685 | 3.65 | 2.2 |
| 足下　无结构对照（0.1.0 码位） | 5.02 | 97.04% | 2.96% | 0.603 | 3.57 | 1.75 |
| **足下 0.2.0　全拼＋结构＋任意两部件** | **6.02** | **98.27%** | **1.73%** | 0.779 | 3.75 | **1.43** |

† 应物一行是上游公布值，不是我这边跑的。足下两行是 `measure_zuxia.py` 的实测输出。

逐级（0.2.0）：

| 级 | 平均键长 | 首选 | 前三 | 平均候选 |
|---|---:|---:|---:|---:|
| 全拼 | 2.97 | 56.79% | 80.65% | 38.1 |
| ＋结构 | 3.96 | 74.43% | 92.93% | 13.4 |
| ＋部件１ | 4.99 | 90.86% | 98.74% | 4.0 |
| ＋部件２ | 6.02 | 98.27% | 99.96% | 1.4 |

「＋结构」这一级（74.43%／13.4）与应物的同一级（73.9%／14.4）几乎重合 ——
这是口径正确的一个旁证：同一套码，测出同一个数。

### 1.3 为什么值得多按那一键

账要照实算：0.2.0 **每字多按 0.18 键**（3.75 对 3.57），不是免费的。买到的是：

- 需要动手选字的比例 2.96% → **1.73%**（少了 42%）；满码平均候选 1.75 → **1.43**；
- 结构码的**学习成本很低** —— 合体字看一眼就知道左右还是上下，不像部首码要
  "知道哪个是部首、且知道它的通称"。这正是足下当初要绕开的那个坑，绕的是
  部首码，不是结构码；
- **与应物码位对齐**：足下前两段与应物前两段同构，`qingzs`（清）、
  `qingzx`（情）、`yingbg`（应）在 0.2.0 里仍是有效中间码（已抽样实测），
  应物用户的肌肉记忆可以迁移。

两条附带的坑，第二轮审计里查出来的，都记在 `docs/方案升级审计.md`：

- **独体字的结构码猜不到**（山→`b`、口→`s`、月→`b`），因为它是从笔画树推的；
- **逐字与应物是否一致，没验过**。这两条是同一个问题，同一条命令能解决：
  `python data-tools/sync_structure.py ../hengma-native/data/hengma.dict.yaml`
  —— 需要在装了应物的机器上跑，我这边没有那个仓库。

### 1.4 仍然成立的那条硬约束

**结构码不能做成可选的**。若 `qingz` 既可能是「左右结构」又可能是部件
「竹／足／走」，编码就有歧义。只能全有或全无 —— 现在是全有。

对照版本（0.1.0 码位，仅供评估，**不可与正式码混用**）：

```bash
python data-tools/generate_zuxia.py --no-structure --out-dir /tmp/no-structure
```

## 二、部件命名表需要人工复核

这是方案的地基，也是我最没把握的部分。

1,586 种部件里：

- **约 120 种我人工定了**（`data-tools/sources/component-names.yaml`）
- **约 1,460 种按自身读音自动取码** —— 这批是隐患所在

自动取码的前提是「读音即通称」。对「青、工、又、田」这类本身就是常用字的
部件成立，但**一定还有漏网的分歧**，就像我已经抓到的这几个：

```
彳  读 chì，通称「双人旁」      → 已收 s 和 c 两个码
丷  数据给 h，通称「八字头」    → 已改为 b
冂  读 jiōng，通称「同字框」    → 已收 t 和 j
```

**建议做法**：跑一遍脚手架，它会按覆盖字数排序列出全部部件：

```bash
python data-tools/build_component_sheet.py
# 输出 data-tools/sources/component-names.tsv
```

从覆盖字数最多的往下看，凡是「读音和你平时的叫法不一样」的，就往
`component-names.yaml` 里加一条。**一个部件可以有多个名称，不必二选一**——
多收一个码的代价远小于漏收。

前 100 个部件覆盖 50% 的字次，前 300 个覆盖 73%，从上往下看性价比最高。

## 五、〔已确认〕足下买到的是「更容易」，不是「更快」

**你已确认按「更容易上手」推进。** 修正后的数据支持这个定位，但要注意方向：

足下 0.2.0 的总击键／字是 **3.75**，应物是 **3.65** —— 足下**略慢**（每字多约
0.1 键），而不是"击键数相同"。它换来的是需要动手选字的比例从 5.90% 降到
1.73%（少了 71%），以及**不需要认识部首**：看见哪个部件眼熟就用哪个。

也就是说：足下拿"多按一点键"去买"少停下来选字"和"不用学部首"。对手写输入、
对不熟悉部首通称的人，这是划算的；对追求极限速度的人，不是。
