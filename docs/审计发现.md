## 一、结论先行：「在任何 Windows 设备上都能安装」到什么程度

| # | 项 | 证据 | 状态 |
|---|---|---|---|
| 1 | **Windows 11 ARM64 上原本装不上、还会留垃圾**：`Is64BitOS()` 在 ARM64 上为真 → 用 `Sysnative\regsvr32.exe`（ARM64 版）去注册 x64 DLL → 必然失败 → `setup.cpp` 随即 `UnregisterAt(root)` 把 x86 注册也撤掉，8 MB 文件留在 `%ProgramFiles%\Zuxia`，无注册、无「应用和功能」条目 | `zxcommon.h:30-32,69-72`、`setup.cpp:272-277` | ✅ **已修**：见第四节。现在能装、能列出、在 x86/x64/Arm64EC 应用里可用 |
| 2 | **ARM64 原生应用仍不可用**（Edge ARM64、记事本、资源管理器）。这是架构决定的，不是缺陷：TSF 把输入法 DLL 载进宿主进程，进程只能载入同架构 DLL | 微软文档；`System32\regsvr32.exe` 在 ARM64 上是 `0xAA64` | ⬜ 需要 ARM64X 文本服务 + **MSVC ARM64 版 librime**（上游不发布）。见第四节 |
| 3 | **未签名**：Windows 11 全新安装默认开启 Smart App Control，未签名应用**被拒绝安装**（不是警告）；企业 WDAC/AppLocker 同样拦 | `Get-AuthenticodeSignature` → `NotSigned` | 💰 **只能靠买证书解决**。见第五节 |
| 4 | **兄弟产品（应物）可能被足下的安装器毁掉**：`/dir=` 无校验，两个产品载荷同名（`rime.dll`、`default.yaml`），`PromoteTree` 原地覆盖 | `setup.cpp:445-446`、`Install-Zuxia.ps1:4` | ✅ **已修**：目标目录「非空且不是本产品的」即拒绝 |
| 5 | **安装器里有三条提权路径**（重解析点递归删除、`%TEMP%` 执行、`%TEMP%` 固定名写入） | 见 3.1 | ✅ **已修** |
| 6 | **文本服务侧：约 17 个 Windows 入口点无异常防护** → 异常逃逸即宿主崩溃（Word 丢文档） | `Diagnostics.h:39-49` 的宏定义了但**一处未用** | ⬜ 最高优先，建议在应物上游先修。见 3.2 |

**一句话**：x64 / x86 的 Windows 10、11、Server 上装得上、用得了（**前提是签名**）；
ARM64 上装得上、在模拟应用里用得了，原生应用用不了；Win7/8.1 无实测证据，不写进支持范围。

## 四、ARM64：已从「装不上」改成「装得上、范围说清楚」

### 4.1 查清的事实（都有出处）

| 事实 | 出处 |
|---|---|
| **librime 不发布 Windows ARM64 二进制**：1.17.0 的资产只有 `Windows-msvc-x64` / `-x86`（外加 clang/mingw/macOS），没有 arm64。上游 CI 也没有 ARM64 任务 | librime releases API、`windows-build.yml`、`rime/home#942`（2021 年至今未排期） |
| 但**源码能编 ARM64**：`rime/librime#582`（2022-12 合并）加了 `build.bat` 的 ARM64 支持；MSYS2 `clangarm64` 确有 1.17.0 的 ARM64 包（clang/MinGW，**非 MSVC**） | PR #582、MSYS2 包页 |
| **ARM64 上没有 x64 的 `regsvr32`**：`System32\regsvr32.exe` 是 `0xAA64`，SysWOW64 是 x86，没有 x64 版本 | winbindex ARM64 数据集实测机器类型 |
| **64 位注册表视图是共享的**：ARM64、ARM64EC、x64 模拟进程共用同一个 64 位视图，被重定向的只有 32 位 x86 视图。所以 32 位安装器用 `KEY_WOW64_64KEY` 写的 CLSID，正是 x64 模拟宿主会解析的那一项 | 微软 Registry Redirector 文档 |
| **TSF 配置库 `HKLM\SOFTWARE\Microsoft\CTF\TIP` 是 Shared**，一次注册覆盖所有架构 | 微软文档 + 本机核对（两个视图里 30 个 CLSID 完全一致） |
| 一个 CLSID 在 64 位视图里只能指向**一个文件**，因此不可能同时服务 ARM64 与 x64 模拟宿主——除非该文件是 **ARM64X** | 微软："A 64-bit COM server that both x64 and Arm64 apps call" 正是必须用 ARM64X 的情形 |

### 4.2 已实施（第四节的这次改动）

安装器在 ARM64 上：

1. **不再把 x64 注册失败当致命错误**（`setup.cpp`：致命分支只对 32 位注册保留）；
2. **直接写 64 位视图**发布 CLSID（`KEY_WOW64_64KEY`），因为 `regsvr32` 只是便利工具；
3. **从安装器自身注册 TSF 语言配置**（`ITfInputProcessorProfiles`，镜像 `src/Register.cpp`）——
   ARM64 上 `DllRegisterServer` 根本不会执行，不补这一步输入法不会出现在 Win+Space；
4. **在 `SOFTWARE\Zuxia` 写入 `HostScope=arm64-emulated-hosts-only`**，让支持人员和
   `scripts/verify-install.ps1` 能区分「只在模拟宿主可用」和「注册坏了」；
5. **卸载器对称地直接删键**；`setup.rc` 的完成文案改成如实陈述适用范围与原因。

x64/x86 机器上的行为**一字未变**（那些分支没进入）。

### 4.3 还没做，以及三条路的代价

> **2026-09-27 已决定：暂时不需要 ARM64 原生支持。**
> 保留已实施的「能装 + 如实告知适用范围」这一档，不投 ARM64X 项目。
> 下面的 B / C 两条作为备查保留——如果以后真的要，代价和关键路径就在这里。

| 方案 | 工作量 | 结果 | 判断 |
|---|---|---|---|
| **A. 现在这样**：x64+x86 载荷 + 直接注册 64 位视图 + 如实告知 | 已做（约 1 天） | x86 / x64 模拟 / Arm64EC 应用里可用；ARM64 原生应用不可用 | ✅ **已采用**，这就是当前的支持水准 |
| **B. 另发一个纯 ARM64 版** | 数天 | **是退步**：64 位视图只能放一个文件，放了 ARM64 就丢掉 x64 模拟支持；想两者都要就得两个 CLSID、两条 Win+Space 条目，其中一条必然在部分应用里静默失效 | ❌ 不建议 |
| **C. ARM64X**（Weasel 的做法：ARM64X 转发器 + 两个实档） | 数周起 | 真正两者通吃 | 暂不投。关键路径是 **MSVC ARM64 版 librime**——没人发布，得自己编并长期维护。小狼毫之所以便宜，是因为它把 librime 放在独立 x64 服务进程里，只需一层薄壳；**足下把引擎放在宿主进程内，这条捷径用不了** |

**顺带一条结构性结论**：如果哪天真要做 ARM64X，先做工程方案里早就写着的
「引擎独立宿主进程 + 命名管道」重构，ARM64 就会从「要 ARM64 版 librime」退化成
「一层不需要 librime 的薄壳」，和 Weasel 一样便宜。这个重构本身也顺带解决
3.2 的第 4 条（词典编译阻塞宿主 UI 线程）。

**未验证**（需要一台 ARM64 设备，3 条命令即可）：ARM64 上 `CreateProcess` 对 ARM64X 的
`regsvr32.exe` 究竟怎么起进程；TSF 在配置里的 CLSID 加载失败时是静默跳过还是报错。
本机无法验证——**这条要你或有人在 Snapdragon 设备上实测**。

## 五、需要你花钱：代码签名

**没有证书，「任何 Windows 设备都能安装」这句话在工程上不可能成立**——这不是代码能修的：

- Windows 11 全新安装默认开启 Smart App Control，未签名应用**被拒绝安装**（不是警告）；
- 企业 WDAC / AppLocker 会直接拦；
- 下载来的 exe 带 Mark-of-the-Web，SmartScreen 显示「未知发布者」。

需要买的东西：**OV 或 EV 代码签名证书**（OV 千元级/年，EV 数千元/年；
2023 年起 CA/B 要求私钥放在 FIPS 140-2 Level 2 硬件令牌或云签名服务里，
所以还要算上令牌或云签名的费用）。
选 OV 还是 EV：OV 足以消除「未知发布者」并在多数企业环境通过；
EV 能让 SmartScreen 信誉立刻生效、在 SAC 下更稳。
国内可选的签发机构与价格区间，公开资料里 GlobalSign 与 freebuf 的年度盘点可以对比看。

流水线**已经备好**：`scripts/sign-file.ps1` + `make-setup.ps1 -Sign` 会按正确顺序签三个位置
（两个文本服务 DLL → 卸载器 → 安装包），带 RFC3161 时间戳——顺序错了就会出现
「安装包里躺着未签名 DLL」这种典型错误。**证书一到手，一条命令即可产出签名版。**

两个已知缺口，会在第一次真正签名时一起补：
- 目前 `-Sign` 没签 **`rime.dll`**（第三方运行库，WDAC 的 DLL 规则恰恰会盯它）；
- 签名带时间戳 → **签名产物天然不可复现**。可复现的是未签名构建（已实测逐字节一致），
  第三方验证签名件的路径是「验签 + MANIFEST 哈希 + SBOM」，不是重建。

## 六、审计方法的局限

- 三轮复审用的是**同一个模型**，只是互不通气。它能发现单一视角的盲区（事实证明有效：
  抓到了我写错的 COM 防护结论、抓到了我引入的非 ASCII 打包缺陷），但**不构成独立性**。
- 所有结论来自**读代码 + 读出货二进制的 PE 头/导入表**。凡是需要真机实验才能定的
  （Win7 能否加载、ARM64 上 `regsvr32` 的真实语义、`fForeground` 的含义、
  N 个进程并发编译词典是否损坏 `.bin`），报告里都标成「未验证」并列出了实验怎么做。
- **没有做**：动态测试（fuzzing、污点追踪）、真实应用矩阵实测、渗透测试、合规审计。
