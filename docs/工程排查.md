# 工程排查

日期：2026-09-27
范围：`df\hengma-native`（应物输入法 0.57-heng）与本次为其分出的 `df\yingwu-zuxia`（应物音形足下输入法 0.1.0）

这份文档回答两件事：**应物的工程是怎么搭的**，以及**照这个搭法做足下时，哪些地方会出事**。
第五节是本次的验证记录，第六节是还没做的事。

---

## 一、结论摘要

1. 应物的 TSF 层与编码方案**没有耦合**：方案 id、词典名、目录名、CLSID 一共 13 处字面量，
   换掉即可得到第二个产品。足下已经按这条路做成，**可与应物并存**。
2. 移植中**最危险的一处不是改名，是应物安装器里的一段"清理旧版"逻辑**。
   它按宏指向 `%ProgramFiles%\Hengma` 并 `DeleteTree` + 删注册表键。若只做机械改名，
   这套逻辑会转而指向**应物自己**，装足下就等于卸载应物。本次把整段删掉了（第四节）。
3. 排查发现应物有一处**用户体验问题**值得优先修：**首次输入会卡约 7.7 秒**（实测日志，
   见第三节其一）。这是安装时没有预编译词典造成的，与编码方案无关。
4. 足下现在**有可安装的文本服务了**，但**还没有词组词典**——打 `tiandi` 一个候选都没有
   （实测，见第五节）。这是它目前最影响日常使用的短板。

## 二、应物的工程思路

### 2.1 分层

```text
宿主应用进程
  └─ TSF 框架
       └─ ZuxiaTSF.dll / YingwuTSF.dll        ← 进程内 COM/TSF 文本服务
            ├─ KeyEventSink / KeyHandler      判定吞键，把按键翻译成 librime 的 keycode
            ├─ Composition / CandidateWindow  预编辑、候选窗（高 DPI、无激活弹窗）
            ├─ InputMode / LanguageBar        中英切换、语言栏指示器
            └─ RimeEngine                     librime 适配层：会话、候选快照、编码注释
                 └─ rime.dll（运行时按模块目录显式 LoadLibrary，不进导入表）
                      └─ data\*.yaml          方案与静态词典
```

要点：

- **不依赖任何第三方输入法框架**，自带 `rime.dll`，安装即用。
- `rime.dll` 用 `LoadLibraryExW` 按绝对路径加载（`LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR`），
  所以 DLL 的导入表里只有系统库——本次实测确认（第五节）。
- 无语言模型、无用户学习、无云端；`enable_user_dict: false`，词典权重固定。
- 进程内运行 librime：工程简单、响应快，代价是输入法故障会影响宿主应用。
  方案文档 §5.3 已写明稳定版应迁到独立宿主进程，尚未落地。

### 2.2 数据流

```text
data-tools/sources/{hanzi-dictionary.txt, cjkvi-ids.txt, 8105.dict.yaml}
  → python data-tools/generate_hengma.py     单字：全拼＋结构码＋部首码
  → python data-tools/generate_phrases.py    词组：连续全拼＋最多两级后缀
  → data/*.dict.yaml                         运行时可部署数据
  → python data-tools/generate_codes.py      候选注释表（每字"完整码"）
```

数据生成是**确定性**的、有报告、可复算；`rebuild-data.ps1` 一条命令全量重出。
足下沿用了同一套结构，`generate_codes.py` 已按足下规则改写（见第四节）。

### 2.3 安装与注册链

`YingwuSetup.exe` 是一个 **32 位、单文件、要求管理员权限**的安装程序（所以 x86/x64 Windows 通吃）：

```text
解压内嵌 cabinet → 校验必需文件 → 注销旧版 → 复制到 %ProgramFiles%\Yingwu
  → 授予 AppContainer 访问权 → 预建 %LOCALAPPDATA%\Yingwu\Rime
  → regsvr32 /s（先 x86 后 x64）→ 写 HKLM 产品键与"应用和功能"卸载项
```

几个值得保留的做法：

- 先解压到 `*.new` 暂存目录并校验，**校验通过前不碰现有安装**；
- 双架构共用一个 CLSID，但分别写入各自的 COM 注册视图，顺序固定（x86 先、x64 后）；
- 提前给沙盒应用（Edge、Store 应用）授予读安装目录、写用户目录的权限，
  否则它们每次启动都要重编译词库或直接失败；
- 卸载默认**保留**用户词库缓存，`-PurgeUserData` 才删。

### 2.4 构建

CMake + MSVC 2022，`/W4 /permissive- /utf-8`，静态 CRT（`MultiThreaded`，安装包不依赖 VC 运行库），
x64 与 x86 各出一份。librime 的官方二进制按 SHA-256 固定，随源码包附带（`third_party/`）。

## 三、排查发现

### 其一（建议优先修）：首次输入卡 7.7 秒

**证据**（`%LOCALAPPDATA%\Yingwu\yingwu.log`，2026-09-27，与 `Rime\installation.yaml` 的
`install_time: Sun Sep 27 16:58:26 2026` 对得上）：

```text
16:58:26.386  engine-start: C:\Program Files\Yingwu\x64
16:58:34.131  dictionaries-built: 7718 ms      ← 装完第一次打字，7.7 秒没有任何反应
16:58:34.132  engine-ready: 8183 characters
```

安装当天反复出现 7469 / 7078 / 6641 / 8187 ms；一旦缓存建好（`Rime\build\*.bin`），
后续只有 62 ms。也就是说**每个新用户、每次清缓存后的第一次输入都要等约 7 秒**，
而这 7 秒里输入法没有任何界面提示。

**建议**：安装程序在复制完文件后，先跑一次无界面的引擎初始化把 `build\*.bin` 建好
（等于安装时替用户付掉这笔时间，还能顺手当作载荷完整性验证）。本次给足下做的
`tools\build-engine-test.ps1` + `tools\engine-test.exe` 已经是这样一个探针，
把它作为可选步骤接进 `setup.cpp` 即可。**未实施**，因为那会改动已发布的应物安装器。

### 其二：版本号有四个不同的值

| 位置 | 值 |
|---|---|
| `VERSION`、`hmcommon.h` 的 `HM_VERSION` | `0.57-heng` |
| `CMakeLists.txt` 的 `project(... VERSION ...)` | `0.57.0` |
| `data/hengma.schema.yaml` | `0.57-heng` |
| `data/default.yaml` 的 `config_version` | `0.3.0` |
| `RimeEngine.cpp` 的 `traits.distribution_version` | **`0.3.1-alpha`** |

最后一条是**会被用户看到的**：本机 `%LOCALAPPDATA%\Yingwu\Rime\installation.yaml` 里
`distribution_version` 就写着 `0.3.1-alpha`。建议统一到 `VERSION` 一个来源。
足下已经统一为 `0.1.0`（`VERSION`、`ZX_VERSION`、CMake、schema、librime traits 全一致）。

### 其三：两条安装路径行为不同

仓库里有两条安装路径：

- `installer\Install-Yingwu.ps1`（开发期脚本）只做 regsvr32 —— **不写 HKLM 产品键，也不写
  "应用和功能"卸载项**；
- `YingwuSetup.exe`（正式安装包）会写全。

后果：用脚本装的那份在"应用和功能"里看不到，其卸载器只能回退到"自身所在目录"来推断安装位置
（`uninst.cpp` 的 fallback 分支）。功能上不算错，但两条路的最终状态不一样，容易误判。

### 其四：进程内 librime 的宿主风险（已知，未处理）

`YingwuTSF.dll` 在宿主进程内跑 librime，且有中文标点、输入法切换等大量按键路径。
代码里已经做了防御（`ZUXIA_COM_GUARD` 系列宏把异常挡在 TSF 边界内，不让它穿回宿主），
但方案文档里的"独立宿主进程 + 命名管道"仍是稳定版的正确方向。

### 其五：方案层——结构码

这不是工程问题，但影响编码设计：衡码的结构码信息效率实测只有 57.7%（三分之二的字是左右结构），
足下已按同一标准去掉。**但结构码只能全有或全无**，不能做成可选：若 `qingz` 既可能是
"左右结构"又可能是部件"竹/足/走"，编码就有歧义。

### 其六：其余

- **无代码签名**，安装时 SmartScreen 会告警；
- **不支持原生 ARM64**（只含 x64/x86 文本服务，ARM64 上走 x64 仿真）；
- 仓库里有 `.github/workflows/windows-build.yml`，但没有它的运行记录；
  `MANIFEST.sha256`（139 行）记录的是本机生成时的哈希，与任何一次 CI 都无关；
- `docs\WINDOWS_ACCEPTANCE_CHECKLIST.md` 的应用矩阵、12 小时稳定性、高 DPI 等**全部未打勾**。

## 四、足下这次改了什么

移植脚本：`tools\port_from_yingwu.py`。它从 `../hengma-native` 读出 TSF 层、安装器与构建脚本，
按一张**令牌表**改名后写入本仓库。跑一次 `python tools\port_from_yingwu.py` 即可重放整个移植，
结束时若有任何旧名字残留会报错退出——所以"两份源码的差异"就是这张表，不会有意外的分叉。

### 4.1 身份改动

| 项 | 应物 | 足下 |
|---|---|---|
| Win+Space 显示名 | 应物输入法 | 应物音形足下输入法 |
| 安装目录 | `%ProgramFiles%\Yingwu` | `%ProgramFiles%\Zuxia` |
| 用户目录 | `%LOCALAPPDATA%\Yingwu` | `%LOCALAPPDATA%\Zuxia` |
| 日志 | `...\Yingwu\yingwu.log` | `...\Zuxia\zuxia.log` |
| 文本服务 DLL | `YingwuTSF.dll` | `ZuxiaTSF.dll` |
| 安装包 | `YingwuSetup-0.57-heng.exe` | `ZuxiaSetup-0.1.0.exe` |
| CLSID | `{57A9A4DA-…}` | `{A0073A11-FF52-4185-A655-D0C9171B7850}` |
| Profile GUID | `{C22C0423-…}` | `{699B0EC1-3FDB-415D-89C0-0E55AA2EFFAF}` |
| 保留键 GUID | `{35C3B3A4-…}` | `{7B73DF85-7342-4B2C-9A90-41482526B47B}` |
| 方案 id / 词典 | `hengma` | `zuxia` |
| 注册表 | `SOFTWARE\Yingwu`、`…\Uninstall\YingwuIME` | `SOFTWARE\Zuxia`、`…\Uninstall\ZuxiaIME` |
| 候选窗类名 / 互斥体 | `YingwuIMECandidateWindow` | `ZuxiaIMECandidateWindow` |
| 图标 | 应 | **足**（`make-icon.ps1 -Char 足`） |

CLSID、Profile GUID、目录、注册表键**都必须不同**，否则两个产品会互相顶掉：
同 CLSID 会让后注册的覆盖前者的 `HKCR\CLSID` 并在注册时删掉对方的语言配置文件。
图标也不同，否则 Win+Space 列表里两个"应物"分不清。

### 4.2 删掉的一段：旧版清理（最关键）

应物的安装器里有一段：

```cpp
void RemoveLegacyInstall() {          // 指向 %ProgramFiles%\Hengma、SOFTWARE\Hengma
  ... hm::DeleteTree(legacy); ...
  hm::RemoveKey(HM_LEGACY_ARP_KEY);
  hm::RemoveKey(HM_LEGACY_PRODUCT_KEY);
}
```

它的存在是合理的——应物**取代**了更早的"衡码输入法 0.3.0-alpha"，升级时得把旧的那份注销掉，
否则输入法列表里会出现两个条目。但足下**不取代**任何东西，它是并行的第二个产品。

所以本次把 `HM_LEGACY_*` 宏与这个函数**整段删除**，而不是改名。
这是移植里唯一一处"必须删而不能改"的地方：一旦机械改名，`DeleteTree` 的目标就会变成
应物的安装目录，用户装个足下就会把应物删掉。移植脚本里对此有专门注释。

### 4.3 唯一的行为差异：候选注释上限

应物的部首码是固定后缀，一个字只有**一个**完整码，候选注释天然是一小段字符串。
足下的规则是"任意两个部件、顺序不限"，因此一个字有很多个**同样完整**的码：

```text
行  → hangcc hangcs hangsc hengcc hengcs hengsc xingcc xingcs xingsc   （9 个）
应  → yinggx yinggy yingxg yingxy yingyg yingyx                        （6 个）
```

全打出来会把候选行撑满，所以 `RimeEngine::AnnotateCode` 改成**最多显示 4 个、其余以 `…` 收尾**
（`src\RimeEngine.cpp` 中的 `kMaxCodes`）。这是全文唯一一处非改名的代码改动。

### 4.4 其余调整

- **必需文件清单**：应物要求 `hengma_phrases.dict.yaml`，足下没有词组词典，
  清单改为 `zuxia.schema.yaml` + `zuxia.dict.yaml` + `zuxia_char_codes.dict.yaml`。
  若照抄不改，**每一次安装都会以"安装载荷不完整"失败**（`setup.cpp` 与 `Install-Zuxia.ps1` 各一处）。
- **候选注释表**：新增 `data-tools\generate_codes.py` 与 `data\zuxia_char_codes.dict.yaml`（18,830 行）。
- **`docs\待你定夺.md` 不进安装包**：它是给维护者看的决策记录，CMake 安装规则里已排除。
- **图标**：`scripts\make-icon.ps1` 的默认字改为 足，两个 `.ico` 都是现渲染的。
- **`hm` 前缀**：宏 `HM_` → `ZX_`，命名空间 `hm::` → `zx::`，头文件 `hmcommon.h` → `zxcommon.h`，
  C++ 命名空间 `hengma` → `zuxia`。纯机械改名，编译器与"残留检查"双重把关。

## 七、两份源码树的关系

```text
df\hengma-native\   ← 上游：应物 0.57-heng，已发布、你天天在用
df\yingwu-zuxia\    ← 本仓库：足下 0.1.0，由上面的树移植而来
```

**它们现在是 fork，不会自动同步。** 应物改了一个 TSF bug，足下不会自动拿到。

同步方式：改动应在**上游**做，然后回来重跑

```powershell
python tools\port_from_yingwu.py      # 覆盖本仓库的 src/ installer/ scripts/ CMakeLists.txt VERSION THIRD_PARTY_NOTICES.md
```

代价是**本仓库对 `src/` 的手工改动会被覆盖**。因此：任何只属于足下的源码差异，
都应该写进 `tools\port_from_yingwu.py` 的 `EXTRA_PAIRS` / `DELETIONS` 表
（目前只有两处：候选注释上限、必需文件清单），而不是直接改 `src\`。

如果将来还要第三个产品，或者这个 fork 的同步成本变得碍事，
正确做法是把 TSF 层抽成一份共享源码、按产品参数化构建——**不建议再做第三次复制**。
